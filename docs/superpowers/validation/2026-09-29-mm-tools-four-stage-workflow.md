# mm-tools 四阶段工作流验证记录

## 验证范围

验证 `aiskill/mm-tools/SKILL.md` 是否强制按顺序执行四个阶段，是否只在新增或优化布局时调研网络案例，是否以原项目决定美术风格，以及是否把运行时接入和最终对比作为完成门禁。

用户选择在当前会话直接执行，因此本次没有派发独立子代理；修改前基线采用旧版文本的结构审查和压力场景逐条推演，修改后采用同场景的规则覆盖检查。

## 修改前基线（RED）

### 场景 A：新界面、已有竞品截图、期限紧

旧版要求调研成熟案例，但没有明确声明外部案例只能决定功能布局与交互，也没有要求从原项目提取字体、配色、材质、线条和视觉密度。执行者可能将竞品截图同时当作美术风格目标。

### 场景 B：优化现有布局、PNG 已提前生成

旧版使用八条连续步骤，没有“不准跳过、合并、倒置或事后补做”的总门禁，也没有规定某阶段无需修改时仍须检查并记录。执行者可能直接验证图片和绑定资源，略过布局结论、Manifest 计划或功能测试。

### 场景 C：图片已复制、绑定代码已写、没有运行截图

旧版要求绑定资源和运行截图，但没有明确否定“文件存在或写好绑定代码即算接入完成”。在时间和沉没成本压力下，执行者可能将文件落盘误报为完成接入。

### 基线失败模式

- 四阶段边界和阶段门禁不明确，允许把步骤当作可合并清单。
- 外部案例的功能参考与原项目美术风格没有清晰的优先级隔离。
- 没有明确要求实际运行 Godot 证明资源已加载显示。
- 差异修正后，没有要求重新执行所有后续阶段。

## 修改后验证（GREEN）

### 场景 A

通过。阶段 1 明确规定仅在新增或优化布局时调研至少两个成熟商业案例；案例只影响功能结构、布局、信息层级、操作路径和反馈。美术提示词必须来自原项目界面与资源证据，外部案例不得覆盖原项目风格。

### 场景 B

通过。总规则明确禁止跳过、合并、倒置或事后补做；即使判断无需改动，也必须检查、记录依据并通过门禁。阶段 2 要求 Manifest、功能、临时 UI、测试和生成计划全部完成后才可生图。

### 场景 C

通过。阶段 3 明确声明文件存在、复制到目录或写好绑定代码均不算接入完成；必须实际运行 Godot，确认资源加载和显示，并保存运行截图。阶段 4 仍须完成逐项对比。

### 回退与重跑

通过。阶段 4 将功能或布局问题路由回阶段 1/2，将 Manifest、生成或接入问题路由回阶段 2/3，并要求重新执行修正点之后的全部阶段。

- 最终规格对照：通过。四个阶段均包含产物与门禁；调研仅由新增或优化布局触发；原项目风格优先；运行时接入和最终对比均为完成条件。
