# mm-tools 强制四阶段工作流

## 目标

将 `mm-tools` 固化为不可跳过、不可合并、顺序执行的四阶段工作流。每个阶段必须产生可核验结果并通过阶段门禁，才能进入下一阶段；即使判断无需修改，也必须完成检查并记录结论。

## 总体规则

1. 阶段必须按 1 → 2 → 3 → 4 执行。
2. 禁止先生成图片再补布局分析、Manifest 或功能实现。
3. 任一阶段验收失败时，返回负责该问题的阶段修正，并重新执行其后的所有阶段。
4. 网络案例用于功能布局和交互依据；美术风格以原项目为第一依据。
5. 阶段结果写入同功能的设计或验收记录，并在最终报告中逐项列出。

## 阶段 1：功能定位与布局确定

先检查用户目标、现有场景、脚本、资源和交互，明确功能边界、信息层级、操作路径、布局和状态反馈。

只有新增布局或优化布局时，才强制联网调研至少两个同品类、已商业化且设计成熟的产品。记录可核验来源，并说明采用与不采用的设计及其项目适配方式。外部案例只提供功能结构、信息层级、操作路径与状态反馈参考，不决定本项目的美术风格。

美术风格必须从原项目的现有界面、图片资源、字体、配色、材质、线条和视觉密度中归纳。原项目证据不足时，使用最接近的已有功能作为基准并记录假设，不得直接复制外部案例风格。

本阶段产物：

- 功能定位、布局结构和交互状态说明；
- 新增或优化布局时的案例调研与适配说明；
- 原项目美术风格证据与风格约束；
- 可运行、可读的临时 UI 或现有布局无需调整的明确结论。

以上产物齐全后，布局才算确定。

## 阶段 2：Manifest JSON 与功能实现

布局确定后，创建或更新 `art_source/manifests/<feature>.json`，同时实现完整功能、交互和临时 UI。Manifest 必须覆盖所有视觉元素及其生成、尺寸、透明、输出和 Godot 绑定信息；提示词继承阶段 1 提取的原项目美术风格。

运行 Manifest `validate`、`plan`、相关功能测试和临时 UI 运行检查。功能在没有生成资源时仍必须可用。校验、测试或运行检查未通过，不得进入生图阶段。

本阶段产物：已验证的 Manifest、可运行功能、临时 UI、测试结果和生成计划。

## 阶段 3：生成资源并接入功能

先汇总生成批次、费用或调用范围、美术方向和覆盖风险，并取得用户确认。随后按 Manifest 生图，运行输出验证，再将通过验证的资源按显式节点路径和属性绑定接入功能。

必须在 Godot 实际运行时确认新资源已被加载和显示。仅生成文件、复制到资源目录或只写绑定代码，均不算完成接入。无效或缺失资源继续使用临时 UI，并回到本阶段修正。

本阶段产物：通过验证的图片、生成报告、运行时绑定和接入后的截图。

## 阶段 4：对比实现与最终验收

将最终运行截图逐项对比：

- 阶段 1 确定的功能定位、布局和交互状态；
- 原项目美术风格证据与约束；
- 外部成熟案例中明确采用的功能布局和交互原则；
- Manifest 中定义的资源与绑定；
- 不同状态和必要分辨率下的实际效果。

记录符合项、差异、原因和修正结果。功能或布局问题返回阶段 1 或 2；资源生成或接入问题返回阶段 2 或 3。修正后重新执行后续阶段，直到对比无未处理差异。

本阶段产物：最终截图、逐项对比报告、差异修正记录和完成结论。

## 实施范围

本次只优化 `aiskill/mm-tools/SKILL.md` 的流程说明与门禁表达，不改变现有 Manifest Schema、生成接口、密钥处理、禁止覆盖规则或 Godot 加载协议。使用行为场景和现有校验工具验证技能说明能够驱动四阶段完整执行。
