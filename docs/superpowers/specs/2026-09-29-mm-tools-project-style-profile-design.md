# mm-tools 项目风格档案设计

## 目标

将 `mm-tools` 优化为可跨 Godot 项目复用的美术资源生成工作流。每次生成前必须从目标游戏自身提取可核验的视觉语言，并将其转化为结构化风格档案、Manifest 约束和验收标准，使新资源既符合功能需求，也与游戏现有画面统一、舒适、美观。

本设计不把《最后的向日葵》的具体美术方向写死在技能中。该项目的美术规范和资源只是当前项目的风格证据；技能应用到其他项目时，应重新提取对应项目的风格档案。

## 范围

- 优化 `aiskill/mm-tools/SKILL.md` 的四阶段流程与完成门禁。
- 扩展 Manifest 对风格来源、风格锚点和负面约束的表达与校验。
- 复用 `sprite-gen` 的图片生成提示词契约与输出验证能力，避免 `mm-tools` 维护一套脱离生成器的提示词规则。
- 增加可自动检查的提示词完整性和风格证据规则。
- 补充测试，确保缺少必要风格信息时无法进入生成阶段。
- 保留现有 Godot 实机验收、`mm-api / gpt-image-2`、资源绑定、安全和分支约束。

本次不重做具体游戏界面，不批量重新生成已有资源，也不把外部商业游戏的美术风格作为生成依据。

## 核心原则

### 项目证据优先

美术风格必须来自当前游戏已经采用的视觉语言。证据按以下优先级使用：

1. 项目美术规范、设计系统和已批准的功能设计文档；
2. Godot 实际运行截图；
3. 已接入游戏并在运行时显示的代表性资源；
4. 同项目已通过验收的 Manifest、提示词和验收记录。

外部案例只可用于功能结构、信息层级和交互方式研究，不能覆盖项目自身的美术方向。未接入游戏的概念图、临时生成图和来源不明的图片不能单独作为风格基准。

### 风格必须可追溯

每条风格结论都应能追溯到文件、截图或运行界面。不得只写“高级感”“舒服”“精致”“符合游戏风格”等不可验证形容词。若项目证据不足，应记录缺口和保守假设，优先沿用最接近的现有功能，而不是自由创造全新风格。

### 舒适服务于功能

“舒适美观”不是增加更多装饰，而是让画面主次清楚、留白稳定、密度适中、色彩克制、状态易辨、连续观看不疲劳。装饰、发光、纹理和高对比区域必须服从可读性与操作效率。

## 风格采样

阶段 1 在布局确定后、资源拆分和提示词编写前执行风格采样。

默认采样范围为：

- 所有直接相关的美术规范或设计系统文档；
- 1–3 张来自 Godot 实际运行的代表性截图；
- 3–8 个已在游戏中使用的代表资源，覆盖与本次任务相关的背景、面板、按钮、图标、角色或场景类别；
- 同类功能已有的状态组，例如默认、悬停、按下、禁用和选中。

采样数量是默认值，不是机械配额。小项目可使用更少证据，但必须覆盖本次资源类型；大型项目应优先选择与目标功能最接近且已通过验收的样本，避免无目的地扫描整个资源库。

## 结构化风格档案

每个功能 Manifest 的 `style` 应包含或引用一份项目风格档案。档案至少描述：

- `evidence`：证据路径、类型和采用原因；
- `medium`：二维手绘、像素画、矢量、3D 渲染等媒介语言；
- `shape_language`：轮廓、圆角、边框、比例和构图特征；
- `palette`：主色关系、强调色、警告色、明度和饱和度边界；
- `materials`：纸张、金属、玻璃、织物、植物等材质与纹理表现；
- `lighting`：主光方向、冷暖关系、发光强度和阴影方式；
- `line_and_edge`：描边、边缘柔硬、透明边缘和抗锯齿要求；
- `detail_density`：主体、次要区域和背景的细节层级；
- `ui_language`：面板、按钮、图标、状态和排版的共同规则；
- `comfort_constraints`：留白、视觉重量、局部对比、发光和纹理密度限制；
- `avoid`：与项目冲突的风格、材质、构图、色彩和常见 AI 瑕疵。

结构化字段保存稳定、可复用的共同约束；单个资源的提示词只补充其功能、构图、尺寸和状态差异，避免每项资源自行重述并逐渐漂移。

## 提示词构造

### sprite-gen 为提示词执行基准

`mm-tools` 负责判断游戏究竟需要什么资源，`sprite-gen` 负责把图片生成请求转换为生成器可执行、可审计的输入。实现时应从当前安装的 `sprite-gen` 文档、CLI 工作流和生成契约中读取与普通图片、透明资源及参考图有关的提示词要求，不复制与 UI 无关的角色动作、动画行或图集约束。

最终提示词仍以 Manifest 为单一事实来源，但必须记录其 `sprite-gen` 契约来源与版本。`mm-tools` 不得依赖记忆中的旧模板，也不得在 `mm_manifest.py` 中长期维护一份与 `sprite-gen` 漂移的完整提示词副本。生成时优先使用 `sprite-gen gen` 支持的提示词文件或等价参数，并继续显式指定项目约定的 provider、model、透明策略和报告路径。

从 `sprite-gen` 提取的是生成器契约，不是资源需求。资源类别、用途、状态、尺寸、九宫格边界、实际显示尺度、项目风格和 Godot 绑定仍必须由 `mm-tools` 根据当前游戏确定。若 `sprite-gen` 的通用默认与游戏需求冲突，以经确认的游戏资源契约为准，并在计划中记录覆盖原因。

### 游戏资源语义

每个启用生成的资源提示词由以下信息组成：

1. 资源的功能与实际使用场景；
2. 资源类型、构图、透明度和目标尺寸；
3. 来自项目风格档案的共享风格锚点；
4. 与同批资源保持一致的视角、光源、边缘、材质和视觉重量；
5. 状态资源之间允许变化和必须保持不变的部分；
6. 与项目冲突的负面约束和通用 AI 瑕疵禁令；
7. 实际显示尺寸下的可读性与细节上限。

对于 UI 资源，提示词还必须明确其工程语义，而不能只描述“画一个好看的界面元素”：

- 面板：用途、内容安全区、边框宽度、可拉伸区域、中心区域纹理密度；
- 按钮：交互状态、固定轮廓、文字禁区、图标位置和状态间允许变化；
- 图标：功能含义、外接框、视觉重量、轮廓优先级和小尺寸辨识要求；
- 条形槽与进度条：填充方向、端帽、轨道与填充层关系；
- 背景与插画：主体避让区、UI 覆盖区、焦点位置和允许裁切范围；
- 九宫格资源：四边不可拉伸区域与中心可拉伸区域，禁止生成依赖固定文字或精确像素重复的装饰。

每项 UI 资源必须先证明它是运行时真正需要的独立图片。纯色、简单渐变、规则描边和可由 Godot Theme 稳定绘制的内容，默认不调用图片模型。这样既避免无意义的 AI 装饰，也让生成预算集中在材质、插画、复杂边框和项目特有图标上。

提示词不得引用在风格证据中不存在的艺术家、品牌或外部游戏风格。不得用大量模糊形容词代替具体视觉关系。文字默认继续由 Godot 字体系统绘制，禁止让图片模型生成界面文字。

## 四阶段流程调整

### 阶段 1：建立视觉契约

在原有功能、布局和交互说明基础上，完成风格采样和结构化风格档案。阶段产物必须列出证据、采用规则、舒适度约束、禁用方向和不确定项。

缺少与目标资源类别相关的项目证据时，应先采用最接近的已接入功能并记录保守假设。若该假设会显著改变项目整体美术方向，则停止并向用户确认。

### 阶段 2：生成 Manifest 与提示词审计

Manifest 保存风格证据、结构化档案或档案引用，以及每项资源继承的风格锚点。`validate` 应拒绝以下情况：

- 启用生成但没有项目风格证据；
- 提示词没有共享风格锚点；
- 提示词未记录适用的 `sprite-gen` 图片生成契约来源；
- 缺少与项目冲突项及 AI 瑕疵相关的负面约束；
- UI 资源缺少用途、实际显示尺度或内容安全区等必要工程语义；
- 状态组没有声明共同构图和允许变化范围；
- 风格来源仅为外部案例或未接入项目的临时图片。

`plan` 汇总风格来源、共同锚点、`sprite-gen` 契约来源、UI 工程语义、负面约束和同批一致性要求，供用户在生成前一次性确认。

### 阶段 3：生成与资源组检查

单张资源完成格式、尺寸和透明通道验证后，还要把同一功能的资源作为一个视觉系统检查：

- 构图、视角、光源与边缘处理一致；
- 同类组件的视觉重量、留白和细节密度稳定；
- 状态变化清晰但主体结构不跳动；
- 没有错误文字、水印、脏边、过度锐化、塑料感或无依据的发光；
- 在实际显示尺寸下保持轮廓和功能可读。

单图美观但整组不协调时，阶段 3 判定失败。返工应优先修正偏离项，不无条件重生成已通过且风格稳定的资源。

### 阶段 4：Godot 实机舒适度验收

最终判断必须来自 Godot 实际运行截图，并与同一游戏的既有界面共同评估。除原有上线质量标准外，增加以下检查：

- 新资源看起来属于同一款游戏，而非独立插画拼贴；
- 第一视觉焦点与功能优先级一致；
- 高亮、饱和色、纹理和装饰没有同时堆叠在所有区域；
- 面板、按钮、图标和背景之间有稳定留白与呼吸空间；
- 连续观看时没有大面积刺眼高亮、过密重复纹理或持续视觉噪声；
- 新资源与现有界面的色彩、材质、边缘和密度过渡自然。

最终报告必须分别记录风格一致性、功能可读性和视觉舒适度。任一项存在未处理差异时不得判定完成。

## Manifest 与兼容性

优先以向后兼容方式扩展当前 schema：已有 Manifest 可继续通过基础加载，但在启用新资源生成时必须满足新的风格字段要求。纯文字资源、关闭生成的占位资源和只执行验证的旧 Manifest 不应因为缺少新字段而无条件失效。

具体字段命名和嵌套结构在实施计划中根据现有 schema 与 `mm_manifest.py` 的数据模型确定。不得建立第二套与 Manifest 分离、容易漂移的资源清单。

## 自动化验证

测试至少覆盖：

- 合法的项目风格档案可以通过校验和计划展开；
- 启用生成但缺少项目证据时校验失败；
- 仅使用外部案例作为美术证据时校验失败；
- 缺少风格锚点或负面约束时校验失败；
- 缺少 `sprite-gen` 契约来源或 UI 工程语义时校验失败；
- 可由 Godot Theme 稳定绘制的简单元素不会被无条件列为图片生成任务；
- 同一状态组缺少共同构图约束时校验失败；
- 旧 Manifest 在不新增生成任务时保持兼容；
- 计划输出包含风格来源、`sprite-gen` 契约来源、锚点、UI 工程语义和资源组一致性要求，但不泄露 API key。

自动化检查只验证结构和必要信息，不能替代对生成图片和 Godot 实机画面的人工视觉判断。

## 失败处理

- 风格证据不足或方向错误：返回阶段 1；
- Manifest、提示词继承或状态组约束错误：返回阶段 2；
- 单图瑕疵或资源组不一致：返回阶段 3；
- Godot 中可读性、层级、舒适度或项目一致性不合格：根据根因返回阶段 1、2 或 3。

每次修正后重新执行受影响阶段及其后的全部阶段。禁止以“单图很好看”“大体一致”或“后续再统一”为由绕过返工。

## 完成条件

只有在风格档案有可追溯的项目证据、所有生成提示词继承同一视觉语言、同批资源内部一致、Godot 实机画面与既有游戏风格协调，并且功能可读性与视觉舒适度均不存在未处理差异时，`mm-tools` 才能判定本次美术资源工作完成。
