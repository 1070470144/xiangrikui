# mm工具

这是当前 Godot 项目的功能优先 AI 美术工作流。功能实现和 UI 布局决定需要哪些资源；美术风格取自原项目，外部案例只用于新增或优化布局时的功能与交互参考。

## 自主推进与询问边界

每个阶段都以**可直接发布到生产环境的质量**完成，不交付仅供演示、占位或“之后再完善”的结果。默认根据项目现状、已批准的项目指南、成熟案例和已有约定作出合理判断并自主推进；安全可推断的偏好、次要细节、可逆选择或已有明确默认值不得暂停流程或反复询问用户。缺少非关键资料时，采用风险最低、最容易调整且与现有项目一致的方案，并在结果中简要说明假设。

所有实现、审查和验证任务都必须使用 subagent 执行；主 agent 负责任务拆分、证据汇总、阶段门禁和最终判断。只有三类情况允许暂停并向用户提出一个聚焦问题：即将发生付费生成、不可逆覆盖或迁移，或缺少执行所需的必要授权。付费生成仍必须遵守阶段 2 的强制生成确认，不得以“自主推进”为由跳过。能通过只读检查、批准指南、现有代码、项目资源或安全默认值解决的问题，不得转交用户决定。当前不在 `master` 等违反本技能执行授权边界的情况，按“缺少必要授权”处理。

## 分支约束

所有 `mm-tools` 开发和资源生成工作只允许直接在 `master` 分支进行。开始修改前先检查当前分支；禁止新建或切换到功能分支，也禁止创建 Git worktree。若当前不在 `master`，停止写入并向用户报告当前分支；不得自行切换分支、移动未提交改动或合并到 `master`。

## 预览与验收边界

网页预览不适用本技能。不得创建或打开 HTML、浏览器页面、Web mockup 或网页服务器来预览、评审或验收 Godot 界面，也不得以网页截图代替 Godot 运行结果。布局草图或离线合成图只能用于内部辅助判断，不能作为阶段门禁或完成证据。

所有运行检查、交互检查、资源接入检查和最终截图都必须来自目标 Godot 项目实际运行；需要自动化时使用 Godot CLI、项目测试或 Godot 编辑器，而不是浏览器。只有用户明确要求 Godot Web 导出或浏览器兼容性测试时，才允许使用网页环境，并且网页结果仍不能替代对用户指定目标平台的验收。

## 强制四阶段流程

四个阶段必须按 **1 → 2 → 3 → 4** 顺序执行，不得跳过、合并、倒置或事后补做。即使某阶段判断无需改动，也必须执行检查、记录“无需改动”的依据并通过阶段门禁。任何阶段发现问题时，返回负责该问题的阶段修正，并重新执行其后的全部阶段。

“功能已经能用”“已有参考图”“PNG 已经生成”“只是小改动”和“时间紧”都不是跳过阶段的理由。最终报告必须分别列出四个阶段的产物与验收结果；缺少任一阶段，不得宣称任务完成。

### 阶段 1：确定功能定位与布局

先检查用户目标和项目现状，明确功能边界、信息层级、操作路径、布局、交互状态和状态反馈，并用程序提供可运行、可读的临时 UI。若现有布局无需调整，也必须记录检查依据和结论。

随后建立可追溯的项目美术采样集：从项目已批准的风格指南或设计规范中取样，并选取 **1–3 张 Godot 实际运行截图**与 **3–8 个和本功能最相关的运行时美术资源**。为每项证据记录项目相对路径；运行截图还要记录对应场景、状态和分辨率，资源还要记录其运行用途。基于这些证据明确一个具体、可执行的**视觉锚点**，例如指定现有界面的面板几何、主光方向、边缘处理、视觉重量和信息密度组合；禁止只写“保持项目风格”。同时记录舒适性约束与排除项，包括亮度/对比、饱和度、闪烁、运动强度、纹理/噪声密度、可读性，以及项目明确不采用的风格、材质或表现手法。找不到已批准指南时，记录缺失事实，并以最接近的现有运行界面及资源形成可追溯锚点，不为安全可推断的风格偏好暂停。

只有**新增布局或优化布局**时，才必须联网调研至少 2 个同品类、已商业化且设计成熟的游戏：

- 优先选择与本项目平台、玩法和目标用户相近的案例；记录游戏名、具体界面或功能及可核验来源。
- 只借鉴功能结构、布局、信息层级、操作路径和状态反馈；说明采用项、适配方式及不采用项。
- 外部游戏只能作为**布局与交互参考**，永远不能作为美术权威、视觉锚点或生成提示词的风格来源；禁止复制品牌资产、受版权保护画面或外部案例的美术风格。
- 外部商业游戏的 UI 参考链接或截图只用于布局研究，必须编码为 Manifest `style.evidence` 条目：`kind: "external_reference"`，并在 `reason` 中明确写出 `layout-only`、采用的布局/交互点及不作为美术权威；不得放入 `style.reference_images` 充当项目美术证据。
- 较长分析必须写入项目内已批准且实际存在的设计记录，并编码为 Manifest `style.evidence` 条目：`kind: "accepted_manifest"`、`source` 使用可解析的 `res://` 路径、`reason` 说明批准依据和本功能采用范围。进入阶段 2 前必须验证该 `source` 文件存在；禁止填写尚未创建的规划路径。
- 找不到完全接近的案例时，组合玩法、平台或交互结构最接近的案例，标明差异与推断后继续。

美术方向必须分析原项目已有界面、图片资源、字体、配色、材质、线条、装饰语言和视觉密度。提示词和生成计划必须继承上述可追溯证据、视觉锚点、舒适性约束和排除项；外部案例不得覆盖原项目风格。

**阶段产物：**功能定位、布局与交互说明；新增或优化布局时的案例调研及适配说明；批准指南取样、1–3 张运行截图、3–8 个运行时资源及其可追溯路径；具体视觉锚点、舒适性约束与排除项；临时 UI 或无需调整的结论。

**阶段门禁：**上述产物齐全、布局已确定，才能进入阶段 2。未完成必要调研时，不得确定新增或优化后的布局、拆分美术资源或调用生成模型。

### 阶段 2：生成 Manifest JSON 并实现功能

布局确定后，创建或更新 `art_source/manifests/<feature>.json`，同时完整实现功能、交互和临时 UI。资源缺失时功能仍必须可用，不得完成后再仅靠 AI 看截图猜资源。Manifest 是资源需求、提示词、状态、输出路径和 Godot 绑定的**唯一事实来源（SSoT）**；生成计划、接入代码和验证不得维护相互漂移的副本。

Manifest 必须记录所有视觉元素：资源 ID、类型、用途、生成开关、提示词、尺寸、透明要求、输出路径、状态、Godot 节点和属性绑定。文字也要记录，但默认 `generation.enabled: false`，由 Godot 字体系统绘制。可由 Godot `Theme`、`StyleBox`、颜色、字体、圆角、边框等简单原生图元稳定实现的元素不是 AI 生成任务，应直接实现并在 manifest 中关闭生成。

每个 AI 资源提示词必须严格按以下层次和顺序编写，不能省略、颠倒或用笼统风格词替代：

1. **游戏资源用途：**在具体功能和交互中的职责，以及玩家需要识别的信息。
2. **运行时显示尺寸与安全区：**目标像素尺寸、Godot 中的实际显示尺寸、缩放方式、裁切边界、文字/交互/关键轮廓安全区。
3. **项目视觉锚点：**阶段 1 的项目内证据路径及其可执行视觉特征；不得引用外部游戏作为美术权威。
4. **资源构图与状态契约：**主体位置、朝向、留白、层级、透视、光照、各交互状态差异，以及与相邻 UI/资源的拼接或九宫格要求。
5. **舒适性约束：**亮度、对比、饱和度、闪烁/运动暗示、纹理与噪声密度、轮廓清晰度和小尺寸可读性上限。
6. **项目与 AI 排除项：**项目禁用风格/材质，以及 no text、no watermark、no logo、no unintended objects、no baked UI 等模型常见错误。
7. **透明输出：**明确透明背景、alpha 边缘质量、禁止底色/棋盘格/环境背景；确实需要不透明整图时明确写出例外及原因。

`mm-tools` 负责确定所需资源、Manifest 语义、Godot 节点/属性绑定和运行时验收；已安装的 `sprite-gen` 生成契约负责 provider 调用、请求执行、结果落盘和生成侧校验。不得在本技能中另造 provider 执行协议，也不得让生成器反向决定功能资源清单或 Godot 语义。

运行 `mm_manifest.py validate`、`plan`、相关功能测试和临时 UI 运行检查。把展开后的生成批次、预计调用范围、原项目美术依据和任何覆盖风险一次性汇总给用户确认。尺寸、命名和常规拆分等可由项目约定推断的细节直接采用默认值，不得逐项询问。

**阶段产物：**已验证的 Manifest、可运行功能、临时 UI、测试结果和生成计划。

**阶段门禁：**校验、测试、运行检查全部通过且用户确认生成计划，才能进入阶段 3；未确认前禁止调用模型。

### 阶段 3：生成资源并接入功能

用户确认后运行 `mm_manifest.py generate <manifest> --confirm`，按已安装 `sprite-gen` 生成契约逐项调用固定的 `mm-api/gpt-image-2`；再运行 `mm_manifest.py verify` 检查 PNG、尺寸和透明通道。生成报告不得包含密钥。

同组资源必须作为一个一致性集合审查：比较轮廓与构图几何、主辅光方向和软硬度、边缘处理、视觉重量、纹理与信息密度。任何一项明显漂移都视为整组尚未通过，不得只因单张图片好看而接入。只允许接入 `sprite-gen` 契约和 `mm_manifest.py verify` 均验证通过、且能追溯到 manifest 资源 ID 与输出路径的结果。

通过 `scripts/art_manifest.gd` 读取同一 manifest，按显式节点路径和属性绑定接入通过验证的资源。缺失或无效资源必须保留临时 UI 并报告警告。

资源文件存在、已复制到目录或已写绑定代码都不等于接入完成；必须实际运行 Godot，确认新资源被加载并正确显示，保存接入后的运行截图。

**阶段产物：**通过验证的图片、无密钥生成报告、运行时绑定和接入后截图。

**阶段门禁：**全部目标资源通过生成契约与输出验证、同组一致性检查，并在 Godot 运行时正确显示，才能进入阶段 4。

### 阶段 4：对比实现并最终验收

使用最终运行截图逐项对比：

- 阶段 1 确定的功能定位、布局、信息层级、操作路径和交互状态；
- 原项目风格证据和生成约束；
- 外部成熟案例中明确采用的功能布局与交互原则（仅新增或优化布局任务）；
- Manifest 定义的资源、状态、节点路径和属性绑定；
- 必要分辨率及各关键状态下的实际表现。

对比必须在 Godot 实际运行时进行，并把新界面与阶段 1 选定的现有项目运行截图放在同一验收记录中；不得只对提示词、静态 PNG 或外部案例做主观评价。除功能和绑定差异外，出现相对现有项目**过量辉光、过高饱和度、过重纹理、过多装饰或过多视觉噪声**时必须拒收并返回阶段 2 或 3 修正，即使资源本身技术校验通过。

记录符合项、差异、原因和修正结果。功能或布局问题返回阶段 1 或 2；Manifest、资源生成或接入问题返回阶段 2 或 3。修正后必须重新执行其后的全部阶段，直到不存在未处理差异。

**阶段产物：**最终截图、逐项对比报告、差异修正记录和完成结论。

**完成门禁：**四个阶段均有可核验产物，且对比报告无未处理差异，才可判定完成。

## Manifest 规则

- Schema 固定为 `art_source/schemas/mm_art_manifest.schema.json`，当前 `schema_version` 为 `1`。
- 每个功能一个 manifest，`feature` 和资源 `id` 使用小写 `snake_case`。
- 完整立绘和装饰性插画默认作为一个 `full_image` 资源；只有换装、动画、复用或独立交互需要时才拆层。
- 按钮图片不烘焙文字，交互状态写入 `states`；可拉伸资源使用 `nine_patch` 并记录四边 margin。
- 图标只有在复用、换色、独立动画或状态变化时才单独列出。
- 只有项目内部且已批准作为项目美术材料的概念图可写入 `style.reference_images`，且不能覆盖由功能语义确定的资源列表。外部商业游戏截图或链接禁止写入该字段，必须保持为 `style.evidence` 中 `kind: "external_reference"`、`reason` 明确 `layout-only` 的布局参考。
- 节点路径和属性绑定必须显式声明，禁止仅凭节点名称猜测。

## 命令

```powershell
& $python aiskill/mm-tools/mm_manifest.py validate art_source/manifests/<feature>.json
& $python aiskill/mm-tools/mm_manifest.py plan art_source/manifests/<feature>.json
& $python aiskill/mm-tools/mm_manifest.py generate art_source/manifests/<feature>.json --confirm
& $python aiskill/mm-tools/mm_manifest.py verify art_source/manifests/<feature>.json
```

## 固定生成接口

`mm-api` 是 `sprite-gen` 中的 OpenAI-compatible provider：

- Endpoint：`https://newapi.oairegbox.cc/v1/images/generations`
- Model：`gpt-image-2`
- API key：从同目录的 `config.json` 读取（用户授权本地保存）。
- Provider：始终显式传 `mm-api`，禁止回退到 Codex 或 Grok。

透明要求以 manifest 为准。背景、面板、主体是否拆分取决于运行时缩放、显示、复用和交互边界，而不是强制全部拆到最小图层。

## Godot 接入约定

- 资源默认放在 `res://art_source/generated/mm_tools/<feature>/` 对应的项目目录。
- 文件名使用稳定的小写英文 snake_case，例如 `avatar_01.png`、`avatar_01_background.png`。
- 不删除或覆盖现有用户资源。路径冲突时优先使用新的稳定文件名并同步 manifest 绑定；只有必须覆盖、迁移或会改变既有资源语义时才暂停并请求确认。
- 功能代码可以提前接入 manifest 加载器，但生成结果只有通过校验后才替换临时 UI。

## 安全与报告

API key 只用于请求头，不写入生成报告、终端输出或新的日志字段。生成报告记录 provider、model、prompt、路径和校验信息，但不得记录 Authorization 头。
